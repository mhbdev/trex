# Trex

[English](README.md)

<div dir="rtl">

یک مونولیت ماژولار مبتنی بر Bun و TypeScript برای پژوهش بازار رمزارز، پشتیبانی تصمیم، آزمایش تاریخی (backtest)، معاملهٔ سایه (shadow) و اجرای سفارش اسپات در حساب اعتباری والکس که فقط با فعال‌سازی صریح انجام می‌شود. گردش کار چنددستیاری آن تحلیل موازی بازار/تکنیکال، اخبار، احساسات و توکنومیکس/آن‌چین را با پژوهشگران صعودی/نزولی، مدیر پژوهش، معامله‌گر، بازبین‌های ریسک تهاجمی/محافظه‌کار/بی‌طرف و مدیر سبد دارایی ترکیب می‌کند.

دستیارهای مدل فقط‌خواندنی هستند. آن‌ها می‌توانند شواهد ارائه‌شده و کندل‌های کامل‌شده را بررسی کنند و یافته‌ها یا پیشنهادهایی با ساختار اعتبارسنجی‌شده برگردانند. گردش کار برنامه صریح است و تنها دروازهٔ ریسک قطعی (deterministic) می‌تواند سفارشی را برای آداپتور اجرای واقعی مجاز کند.

## محیط اجرا

- Bun نسخهٔ ۱.۲ یا جدیدتر، TypeScript، Commander، رجیستری ارائه‌دهندگان AI SDK و `ToolLoopAgent`.
- Drizzle ORM با SQLite از طریق درایور بومی SQLite در Bun. این یک استقرار تک‌فرایندی/تک‌اجراکننده است.
- محاسبات اعشاری (Decimal) برای اندازهٔ سفارش، پرشدن‌ها، میزان درگیری سرمایه، کارمزدها و گزارش‌ها.
- REST والکس برای متادیتای بازار اسپات، قیمت‌ها، عمق بازار، کندل‌ها، محدودیت‌های بسته، موجودی‌ها و چرخهٔ عمر سفارش؛ Centrifugo v2 برای سیگنال‌های زندهٔ قیمت عمومی و تغییرات دفتر سفارش.
- فایل اجرایی بستهٔ `trex` کار را به Bun واگذار می‌کند؛ بنابراین می‌توان آن را به‌عنوان CLI لینک یا نصب کرد و همچنان از پشتیبانی SQLite در Bun بهره برد.

## راه‌اندازی

### شروع داشبورد

پیش‌نیاز: دسترسی به اینترنت برای نصب بسته‌ها و استفاده از API صرافی و مدل‌ها. بقیهٔ کارها (Bun، وابستگی‌ها، ساخت داشبورد و کلید رمزنگاری) با یک دستور انجام می‌شود.

**ویندوز** (PowerShell):

</div>

```powershell
irm https://raw.githubusercontent.com/mhbdev/trex/main/setup.ps1 | iex
```

<div dir="rtl">

**macOS یا لینوکس**:

</div>

```bash
curl -fsSL https://raw.githubusercontent.com/mhbdev/trex/main/setup.sh | bash
```

<div dir="rtl">

این اسکریپت اگر Bun نصب نباشد آن را نصب می‌کند، Trex را در `~/trex` دانلود می‌کند (با `TREX_HOME` می‌توانید پوشهٔ دیگری انتخاب کنید)، وابستگی‌ها را نصب می‌کند، در اولین اجرا داشبورد را می‌سازد، سرویس محلی را اجرا می‌کند و `http://127.0.0.1:4173` را در مرورگر شما باز می‌کند. هر بار که Trex را خواستید همین دستور را دوباره اجرا کنید: اگر از قبل در حال اجرا باشد فقط داشبورد را باز می‌کند، وگرنه آن را راه می‌اندازد. برای توقف سرویس در همان ترمینال Ctrl+C بزنید. اولین اجرا همچنین یک میان‌بر **Trex** روی دسکتاپ شما می‌گذارد که Trex را به همین شکل اجرا یا باز می‌کند (در ویندوز یک فایل `.lnk`، در macOS فایل `Trex.command` و در لینوکس فایل `Trex.desktop`)؛ اگر نمی‌خواهید، پیش از اجرای اسکریپت `TREX_NO_SHORTCUT=1` را تنظیم کنید.

از داخل یک کلون موجود، در ویندوز `.\setup.ps1` را اجرا کنید (یا روی `setup.cmd` دوبار کلیک کنید) و در macOS یا لینوکس `./setup.sh` را. اگر Bun از قبل نصب است، `bun run start` در پوشهٔ پروژه همین کار را می‌کند؛ `bun run start -- --port 4174` پورت دیگری انتخاب می‌کند و `--no-open` باز کردن مرورگر را رد می‌کند.

در یک پروفایل تازه، داشبورد **راه‌اندازی سریع** را باز می‌کند؛ یک ویزارد سه‌مرحله‌ای: سرویس هوش مصنوعی، مدل و کلید API را انتخاب کنید؛ ارز بازار پایهٔ والکس و جفت‌ارزهای مجاز را برگزینید (اطلاعات دسترسی حساب والکس بخشی اختیاری است و فقط برای نمایش موجودی واقعی و معاملهٔ واقعی لازم است)؛ سپس اعتبارسنجی و بررسی سلامت را اجرا کنید. کلیدها در همان لحظه به‌صورت رمزگذاری‌شده ذخیره می‌شوند، ویزارد را هر زمان می‌توان از نوار کناری دوباره باز کرد و هر مقداری را بعداً می‌توان در **پروفایل‌ها و تنظیمات** تغییر داد یا در **سلامت سیستم** بررسی کرد. با یک آزمایش تاریخی یا اجرای سایه شروع کنید تا دستیارها و سبد مجازی بدون ارسال سفارش به صرافی به کار بیفتند. فراخوانی API مدل‌ها همچنان ممکن است برای شما هزینه داشته باشد. حالت سایه از دادهٔ زندهٔ بازار والکس استفاده می‌کند؛ آزمایش تاریخی از کندل‌های گذشته.

**کلید رمزنگاری.** اطلاعات دسترسی ذخیره‌شده با کلیدی رمزگذاری می‌شوند که Trex در اولین اجرا به‌صورت خودکار می‌سازد و در فایل `trex-encryption.key` کنار پایگاه داده نگه می‌دارد (محل پایگاه داده در ادامه آمده است). از این فایل همراه با پایگاه داده نسخهٔ پشتیبان بگیرید: بدون آن، اطلاعات دسترسی ذخیره‌شده قابل بازیابی نیستند. دستور `bun run trex secrets status` نشان می‌دهد کلید فعال از کجا می‌آید و `bun run trex secrets rekey` (یا دکمهٔ **تعویض کلید اصلی** در صفحهٔ پروفایل‌ها) کلید تازه‌ای می‌سازد، اطلاعات ذخیره‌شده را دوباره رمزگذاری می‌کند و فایل را به‌روز می‌کند. اپراتورهایی که مدیر رمز (secret manager) سیستم‌عامل یا سرویس را ترجیح می‌دهند می‌توانند به‌جای آن `ENCRYPTION_KEY` را تنظیم کنند (یک کلید base64url با ۴۳ نویسه از `bun run trex secrets generate-key`)؛ وقتی این متغیر تنظیم باشد، Trex از آن استفاده می‌کند و هرگز فایل کلید نمی‌نویسد. بستن مرورگر کار موتور را متوقف نمی‌کند؛ توقف سرویس محلی، توقف ایمن اجراهای مدیریت‌شده را درخواست می‌کند.

داشبورد و CLI از یک پایگاه دادهٔ SQLite و پروفایل‌های پیکربندی نام‌دار مشترک استفاده می‌کنند. تنظیمات زمان اجرا و اطلاعات دسترسی ارائه‌دهنده/صرافی از پروفایل فعال پایگاه داده می‌آیند؛ فایل‌های dotenv در شروع عادی بارگذاری نمی‌شوند. برای مهاجرت یک `.env` موجود از `bun run trex profile import-dotenv <path> --name <profile>` استفاده کنید. واردکننده تنظیمات شناخته‌شده را اعتبارسنجی و ذخیره می‌کند، اطلاعات رمزگذاری‌شده را تأیید می‌کند و سپس مقادیر واردشده را از فایل مبدأ حذف می‌کند. داشبورد می‌تواند بررسی سلامت انجام دهد، تنظیمات را اعتبارسنجی کند، بازارها را ببیند، آزمایش تاریخی و اجرای سایه یا اجرای واقعی با تأیید صریح را آغاز کند، گزارش‌ها را مرور کند و سفارش‌های واقعی مرتبط را لغو کند.

### به‌روزرسانی

پایگاه داده، پروفایل‌ها، تاریخچهٔ اجراها و کلید رمزنگاری شما بیرون از پوشهٔ پروژه قرار دارند؛ بنابراین به‌روزرسانی هرگز به آن‌ها دست نمی‌زند. راه‌انداز در شروع بعدی وابستگی‌ها را دوباره نصب می‌کند، اگر فایل‌های منبع تغییر کرده باشند داشبورد را دوباره می‌سازد و مهاجرت‌های پایگاه داده را اجرا می‌کند.

از داخل یک کلون، آخرین تغییرات را بگیرید و دوباره اجرا کنید:

</div>

```powershell
git pull
.\setup.ps1
```

```bash
git pull && ./setup.sh
```

<div dir="rtl">

یا بگذارید خود اسکریپت راه‌اندازی این کار را انجام دهد: در ویندوز `.\setup.ps1 update` و در macOS یا لینوکس `./setup.sh update`. اگر با دستور یک‌خطی نصب کرده‌اید و هرگز کلون نکرده‌اید، همان دستور را با پرچم به‌روزرسانی دوباره اجرا کنید؛ آخرین کد را در همان پوشه می‌گیرد (اگر پوشه یک کلون git باشد با `git pull`، وگرنه با دانلود آرشیو روی آن):

</div>

```powershell
$env:TREX_UPDATE = 1; irm https://raw.githubusercontent.com/mhbdev/trex/main/setup.ps1 | iex
```

```bash
curl -fsSL https://raw.githubusercontent.com/mhbdev/trex/main/setup.sh | TREX_UPDATE=1 bash
```

<div dir="rtl">

پیش از به‌روزرسانی، Trex را (با Ctrl+C) متوقف کنید تا نسخهٔ جدید تمیز شروع شود؛ میان‌بر دسکتاپ پس از به‌روزرسانی همچنان کار می‌کند.

### حذف نصب

Trex سه چیز روی رایانه به‌جا می‌گذارد: پوشهٔ پروژه (به‌طور پیش‌فرض `~/trex` یا هر جایی که کلون کرده‌اید)، پوشهٔ داده شامل پایگاه داده و کلید رمزنگاری، و میان‌بر دسکتاپ. Bun برنامهٔ جداگانه‌ای است و نصب می‌ماند مگر آن را هم حذف کنید. ابتدا Trex را با Ctrl+C در ترمینال آن یا با بستن همان پنجره متوقف کنید.

**ویندوز** (PowerShell). پوشهٔ پروژه و میان‌بر دسکتاپ را حذف کنید و داده‌ها را نگه دارید:

</div>

```powershell
Remove-Item -Recurse -Force "$HOME\trex"; Remove-Item -Force (Join-Path ([Environment]::GetFolderPath("Desktop")) "Trex.lnk") -ErrorAction SilentlyContinue
```

<div dir="rtl">

برای حذف پایگاه داده، پروفایل‌ها، تاریخچهٔ اجراها و کلید رمزنگاری هم (پس از آن اطلاعات دسترسی ذخیره‌شده قابل بازیابی نیستند):

</div>

```powershell
Remove-Item -Recurse -Force "$env:LOCALAPPDATA\trex", "$env:LOCALAPPDATA\wallex-trading-agents" -ErrorAction SilentlyContinue
```

<div dir="rtl">

برای حذف Bun هم، پوشهٔ آن را پاک کنید و ورودی‌اش را از PATH کاربر بردارید:

</div>

```powershell
Remove-Item -Recurse -Force "$HOME\.bun"; [Environment]::SetEnvironmentVariable("Path", (([Environment]::GetEnvironmentVariable("Path", "User") -split ";") | Where-Object { $_ -and $_ -notlike "*\.bun\bin*" }) -join ";", "User")
```

<div dir="rtl">

**macOS یا لینوکس** (ترمینال). پوشهٔ پروژه و میان‌برها را حذف کنید و داده‌ها را نگه دارید:

</div>

```bash
rm -rf ~/trex ~/Desktop/Trex.command ~/Desktop/Trex.desktop ~/.local/share/applications/trex.desktop
```

<div dir="rtl">

برای حذف پایگاه داده، پروفایل‌ها، تاریخچهٔ اجراها و کلید رمزنگاری هم (پس از آن اطلاعات دسترسی ذخیره‌شده قابل بازیابی نیستند)، خط مربوط به سیستم خود را اجرا کنید:

</div>

```bash
rm -rf ~/Library/Application\ Support/trex ~/Library/Application\ Support/wallex-trading-agents   # macOS
```

```bash
rm -rf ~/.local/share/trex ~/.local/share/wallex-trading-agents   # Linux
```

<div dir="rtl">

برای حذف Bun هم، `~/.bun` را پاک کنید و خط‌های `BUN_INSTALL` و PATH را که نصب‌کنندهٔ Bun به پروفایل شل شما (`~/.bashrc`، `~/.zshrc` یا `~/.profile`) اضافه کرده بود بردارید:

</div>

```bash
rm -rf ~/.bun
```

<div dir="rtl">

اگر با `TREX_HOME` در پوشهٔ دیگری نصب کرده‌اید یا Trex را با `--database-url` سفارشی اجرا کرده‌اید، همان مسیرها را به کار ببرید؛ فایل کلید کنار همان پایگاه داده قرار دارد.

### استفاده از CLI

راه‌اندازی راهنما پیکربندی را در پروفایل فعال پایگاه داده ذخیره می‌کند. یک بار آن را اجرا کنید، تنظیمات را بررسی کنید و سپس یک اجرای سایهٔ تک‌چرخه آغاز کنید:

</div>

```powershell
bun run trex configure --mode shadow
bun run trex doctor --mode shadow --check-wallex
bun run trex shadow --symbol BTCTMN --strategy agentic-balanced --html reports/first-shadow.html
```

<div dir="rtl">

برای ارزیابی سایهٔ پیوستهٔ یک‌دقیقه‌ای، `--watch --interval-seconds 60` را اضافه کنید. حالت سایه هرگز نویسندهٔ سفارش صرافی نمی‌سازد. برای دیدن دستورها و گزینه‌ها از `bun run trex --help` و `bun run trex <command> --help` استفاده کنید. [راهنمای موتور](packages/engine/README.md) گردش کار، مناظرهٔ دستیارها و حافظه، بررسی‌های ریسک، سبدهای دارایی و ردّ ممیزی را توضیح می‌دهد.

پایگاه دادهٔ پیش‌فرض SQLite در پوشهٔ دادهٔ برنامه‌های کاربر فعلی سیستم‌عامل ذخیره می‌شود (`~/AppData/Local/trex/trex.sqlite` در ویندوز، `~/Library/Application Support/trex/trex.sqlite` در macOS و `~/.local/share/trex/trex.sqlite` در لینوکس). اگر پایگاه داده‌ای از نسخهٔ قدیمی‌تر Trex وجود داشته باشد، Trex همان را به کار می‌برد تا پروفایل‌ها و تاریخچهٔ اجراها در دسترس بمانند. برای استفاده از پایگاه دادهٔ دیگر، گزینهٔ فقط‌راه‌اندازی `--database-url` را بدهید، مثلاً `bun run trex --database-url file:./data/trex.sqlite ui`؛ محل پایگاه داده یک تنظیم پروفایل نیست چون موتور باید پیش از خواندن تنظیمات بداند پایگاه داده کجاست. هنگام وارد کردن یک فایل dotenv قدیمی که `DATABASE_URL` آن به پایگاه دادهٔ غیرپیش‌فرض اشاره می‌کرد، همان مسیر را به‌عنوان `--database-url` به دستور وارد کردن بدهید. فایل‌های مهاجرت نسبت به موتور نصب‌شده پیدا می‌شوند؛ بنابراین دستورهای پایگاه داده از پوشهٔ دیگری هم کار می‌کنند.

برای یک زیرحساب اعتباری واقعی، کلید API والکس مخصوص همان حساب را با دسترسی خواندن و معامله و بدون دسترسی برداشت پیکربندی کنید. `WALLEX_SUB_ACCOUNT_CLIENT_ID`، `WALLEX_PACKAGE_ID`، `WALLEX_ALLOWED_MARKETS`، `LIVE_MAX_GROSS_EXPOSURE` و `WALLEX_ENABLE_LIVE_TRADING` را با داشبورد یا `trex config set` در پروفایل فعال ذخیره کنید. تا زمانی که `LIVE_MAX_GROSS_EXPOSURE` صفر باشد حالت واقعی شروع نمی‌شود. این سقف مطلق برحسب `WALLEX_QUOTE_CURRENCY` است و مجموع ارزش موقعیت‌های باز موتور را محدود می‌کند؛ با `RISK_MAX_GROSS_EXPOSURE` و هر سقف سخت‌گیرانه‌تر استراتژی ترکیب می‌شود. موتور همچنین پیش از فعال کردن هر بازار، `unavailableMarkets` بستهٔ پیکربندی‌شده را دریافت می‌کند. برای زیرحساب اعتباری چالش از کلید حساب اصلی استفاده نکنید.

### شناسه‌های اعتباری والکس و بودجهٔ درگیری سرمایه

- **شناسهٔ بسته (Package ID)** تعریف طرح اعتباری را مشخص می‌کند (خود طرح، نه حساب شخصی شما و نه مبلغ وام). آن را در فهرست [بسته‌های اعتبار معاملاتی فعال](https://developers.wallex.ir/docs/trade-credit-active-packages) والکس پیدا کنید و با همان شناسه [جزئیات بسته](https://developers.wallex.ir/docs/trade-credit-package-details) را ببینید. API جزئیات `GET /v1/prop/packages/{id}` است؛ موتور `unavailableMarkets` را از همین نقطهٔ پایانی می‌خواند. کارت طرح در تصویر، اعتبار و دکمهٔ فعال‌سازی را نشان می‌دهد اما شناسهٔ عددی بسته را نه. اگر طرح همچنان دکمهٔ فعال‌سازی دارد، پیش از استفاده از اطلاعات دسترسی حساب، در بخش اعتبارهای فعال/تاریخچه بررسی کنید که بسته واقعاً فعال شده باشد.
- **شناسهٔ مشتری زیرحساب (Sub-account client ID)** حساب اعتباری شخصی ساخته‌شده با فعال‌سازی را مشخص می‌کند. حساب‌های فعال را در [فهرست زیرحساب‌های فعال](https://developers.wallex.ir/docs/trade-credit-active-sub-account-list) والکس ببینید که فیلد پاسخ آن `clientId` است، یا [تاریخچهٔ حساب اعتبار معاملاتی](https://developers.wallex.ir/docs/trade-credit-sub-account-history) را بررسی کنید که در آن `client_id` نام دارد. این مقدار را از ردیف حساب اعتباری فعال کپی کنید. این مقدار به‌عنوان هدر `sub-account-client-id` ارسال می‌شود و هم با شناسهٔ بسته و هم با `client_id` هر سفارش موتور متفاوت است.
- **کلید API** یک راز جداگانه است. کلیدی مخصوص زیرحساب اعتباری با دسترسی خواندن و معامله و بدون دسترسی برداشت بسازید/به کار ببرید. هرگز آن را در گفت‌وگو نچسبانید یا در مخزن ثبت نکنید.

والکس دارایی ورودی بسته را وثیقهٔ کاربر می‌داند: زیان‌ها هنگام بسته شدن بسته از آن کسر می‌شوند. اعتبار همچنین کارمزد روزانه دارد. رسیدن به حد هشدار ممکن است به بستن یا افزودن وثیقه نیاز داشته باشد؛ رسیدن به حد لیکوئید شدن، بسته را خودکار می‌بندد. اگر کیف پول اصلی [برای شارژ خودکار متصل باشد](https://developers.wallex.ir/docs/trade-credit-connect-wallet)، والکس ممکن است هنگام عبور بسته از حد هشدار، دارایی کیف پول اصلی را منتقل کند. سقف درگیری سرمایهٔ موتور، این قواعد بستهٔ والکس را تغییر نمی‌دهد و نمی‌تواند حداکثر زیان کل حساب را تضمین کند. اگر نمی‌خواهید از کیف پول اصلی انتقالی انجام شود، شارژ خودکار را قطع کنید و پیش از هر سفارش واقعی، وام فعلی، وثیقه، سطوح هشدار/لیکوئید و کارمزد روزانهٔ بسته را در والکس بررسی کنید.

برای کوچک نگه داشتن درگیری سرمایهٔ واقعی موتور، یک سقف سخت صریح و سقف‌های کوچک‌تر برای هر سفارش/موقعیت تعیین کنید. برای مثال، **فقط اگر والکس وام ۵٬۰۰۰٬۰۰۰ تومانی را تأیید کند**، مقدار `LIVE_MAX_GROSS_EXPOSURE` برابر `100000` تومان ۲٪ آن وام است؛ این مقدار ارزش کل موقعیت‌های باز ایجادشده/نگه‌داشته‌شده در حساب اعتباری را محدود می‌کند، نه مبلغ زیانی که والکس وعده می‌دهد. همچنین `RISK_MAX_ORDER_NOTIONAL=50000`، `RISK_MAX_POSITION_NOTIONAL=75000` و `RISK_MAX_GROSS_EXPOSURE=100000` را تنظیم کنید. از دست رفتن کامل آن سرمایه، کارمزدها، جهش قیمت یا سفارش‌های دستی/خارج از موتور همچنان ممکن‌اند. این سقف به‌طور پیش‌فرض صفر است (معاملهٔ واقعی غیرفعال) و بلافاصله پیش از ارسال سفارش دوباره اعمال می‌شود.

بازارها را می‌توان به شکل نماد والکس (`BTCTMN`) یا جفت خوانا (`BTC/TMN`) وارد کرد؛ CLI هر دو را نرمال می‌کند. با فهرست مجاز کوتاهی مانند `BTCTMN,ETHTMN,USDTTMN` شروع کنید. این‌ها در فید عمومی فعلی بازار، بازارهای اسپات فعال بودند و در فهرست جفت‌های محدودشده‌ای که شما دادید نبودند. `USDTTMN` بازار تبدیل تتر/تومان است، نه یک جفت معاملاتی رمزارز/تومان دیگر. فعال بودن فعلی یک بازار اسپات هنوز ثابت نمی‌کند بستهٔ شما آن بازار را مجاز می‌داند: پاسخ `unavailableMarkets` مخصوص بسته پیش از تصمیم‌های سایه/واقعی بررسی می‌شود. فید عمومی بازار والکس و حجم‌های ۲۴ ساعته تغییر می‌کنند؛ پس پیش از معامله با `trex markets --all` و بستهٔ خود دوباره بررسی کنید.

## پیکربندی از CLI

برای راه‌اندازی راهنما از `configure` استفاده کنید؛ این دستور اطلاعات دسترسی AI را که وجود ندارد با ورودی پنهان می‌پرسد و پیش از فعال کردن دسترسی سفارش واقعی تأیید صریح می‌خواهد. تنظیمات لازم همچنین می‌توانند هنگام شروع یک دستور تعاملی آزمایش تاریخی، سایه یا واقعی به‌صورت خودکار گردآوری شوند. در اجراهای غیرتعاملی، نبودِ تنظیمات پیام راه‌اندازی تولید می‌کند؛ با `--no-prompt` می‌توانید پرسش‌ها را خاموش کنید.

</div>

```powershell
bun run trex configure --mode shadow
bun run trex config show
bun run trex config set AI_API_KEY # prompts with hidden input
bun run trex config set ENGINE_STRATEGIES_JSON '[{"id":"momentum-lite","name":"Momentum Lite","mandate":"Only trade with the completed-candle trend; otherwise HOLD.","minConfidence":0.7,"allowedOrderTypes":["LIMIT"]}]'
bun run trex config unset AI_API_KEY
```

<div dir="rtl">

برای محیط‌های مستقل از پروفایل‌های نام‌دار استفاده کنید: `trex profile list`، `trex profile create "Shadow lab"`، `trex profile use <profile-id>` و `trex profile delete <profile-id>`. پروفایل فعال پایگاه داده منبع حقیقت زمان اجراست. اولویت چنین است: **بازنویسی‌های تک‌دستوری CLI ← پروفایل فعال پایگاه داده ← پیش‌فرض‌های داخلی**. گزینه‌های CLI و `--set KEY=VALUE` فقط بر همان فراخوانی اثر می‌گذارند؛ ویرایش‌های داشبورد و `trex config set` در پروفایل فعال ماندگار می‌شوند. اطلاعات دسترسی ارائه‌دهنده، والکس و منابع داده در SQLite رمزگذاری می‌شوند و هرگز به مرورگر برگردانده نمی‌شوند. دو مقدار راه‌اندازی عمداً خارج از پروفایل‌ها هستند: `DATABASE_URL` پایگاه داده را پیش از باز شدن انتخاب می‌کند و کلید رمزنگاری از رازهای رمزگذاری‌شدهٔ پروفایل محافظت می‌کند. Trex آن کلید را در فایلی کنار پایگاه داده مدیریت می‌کند؛ اپراتورهایی که مدیر رمز را ترجیح می‌دهند می‌توانند `ENCRYPTION_KEY` را بدهند که همیشه اولویت دارد. کلید را هرگز در SQLite یا فایل dotenv قرار ندهید. `profile import-dotenv` یک ابزار مهاجرت یک‌باره است؛ فایل‌های dotenv هرگز در شروع عادی CLI یا داشبورد بارگذاری نمی‌شوند.

دستورهای عملیاتی بازنویسی‌های تک‌اجرایی مانند `--ai-provider`، `--ai-model`، `--ai-base-url`، `--boxapi-api-key`، `--boxapi-base-url`، `--liara-api-key`، `--liara-workspace-id`، `--liara-base-url`، `--wallex-api-key`، `--wallex-sub-account-client-id`، `--wallex-package-id`، `--wallex-allowed-markets`، `--live-trading`، `--auto-trading`، `--strategy-profiles-json`، `--max-debate-rounds`، `--max-risk-discuss-rounds`، `--memory-holding-period-bars`، `--memory-benchmark-symbol` و `--paper-initial-cash` را می‌پذیرند. `--set KEY=VALUE` از هر تنظیم اعتبارسنجی‌شدهٔ پایگاه داده، از جمله JSON مدل نقش‌ها و سقف‌های ریسک، پشتیبانی می‌کند. گزینه‌های نام‌دار CLI بر `--set` اولویت دارند؛ مقادیر خط فرمان فقط برای همان فراخوانی پروفایل انتخاب‌شده را بازنویسی می‌کنند. `--database-url` پایگاه دادهٔ SQLite را پیش از بارگذاری پروفایل انتخاب می‌کند و در پایگاه داده ذخیره نمی‌شود. دستور `config set` مقادیر را در پروفایل رمزگذاری‌شدهٔ فعال ذخیره می‌کند؛ مقادیر محرمانه هنگام پرسش پنهان می‌شوند و پیش از ذخیره در SQLite رمزگذاری می‌شوند. آرگومان‌های محرمانهٔ خط فرمان ممکن است در تاریخچهٔ شل و فهرست فرایندها دیده شوند؛ پس پرسش پنهان یا فیلدهای فقط‌نوشتنی اطلاعات دسترسی در داشبورد را ترجیح دهید.

کنترل‌های مناظره و حافظه در راه‌اندازی راهنما، پروفایل فعال، `config set` یا به‌عنوان گزینهٔ هر دستور قابل تنظیم‌اند. برای مثال، برای یک آزمایش کاغذی سریع‌تر از `--max-debate-rounds 2 --max-risk-discuss-rounds 1 --memory-holding-period-bars 30` استفاده کنید؛ پنجرهٔ حافظه برحسب بازه‌های یک‌دقیقه‌ای کامل‌شده اندازه‌گیری می‌شود.

`AI_PROVIDER` و `AI_MODEL` ورودی پیش‌فرض رجیستری ارائه‌دهنده و مدل را در پروفایل فعال پایگاه داده انتخاب می‌کنند. ارائه‌دهندگان پشتیبانی‌شده عبارت‌اند از OpenAI، Anthropic، Google، نقاط پایانی عمومی سازگار با OpenAI، BoxAPI و Liara AIaaS. `AI_API_KEY` کلید ارائه‌دهندهٔ پیش‌فرض را می‌دهد و `AI_BASE_URL` یک نقطهٔ پایانی سازگار عمومی را پیکربندی می‌کند. BoxAPI از اطلاعات دسترسی رمزگذاری‌شدهٔ `BOXAPI_API_KEY` استفاده می‌کند و پیش‌فرض آن `https://ai.boxapi.ir/ai/v1` است؛ Liara از `LIARA_API_KEY` رمزگذاری‌شده، `LIARA_WORKSPACE_ID` و `LIARA_BASE_URL` (پیش‌فرض `https://ai.liara.ir`) استفاده می‌کند و مسیر استنتاج مخصوص فضای کاری `/api/{workspaceID}/v1` توسط آداپتور ساخته می‌شود. اطلاعات دسترسی ارائه‌دهنده در پروفایل انتخاب‌شده رمزگذاری می‌شود. برای مسیردهی نقش‌های جداگانه، اطلاعات دسترسی مخصوص هر ارائه‌دهنده را در فیلدهای کلید داشبورد ذخیره کنید یا از پرسش پنهان `AI_PROVIDER_KEYS_JSON` استفاده کنید و سپس `AI_ROLE_MODELS_JSON` را تنظیم کنید:

</div>

```powershell
bun run trex config set AI_ROLE_MODELS_JSON '{"news_analyst":"anthropic:<available-model>","portfolio_manager":"boxapi:<available-model>","trader":"liara:<provider/model>"}'
```

<div dir="rtl">

یا نقش‌ها را به‌صورت بصری در صفحهٔ **دستیارها** داشبورد ویرایش کنید. کلیدهای API ارائه‌دهنده باید در ویرایشگر فقط‌نوشتنی اطلاعات دسترسی داشبورد یا پرسش پنهان `trex config set AI_PROVIDER_KEYS_JSON` قرار بگیرند؛ هرگز آن‌ها را در JSON مسیردهی نگذارید.

در Liara شناسه‌های مدل استنتاج به فضای کاری وابسته‌اند و با [نقطهٔ پایانی مدل‌های در دسترس](https://developers.liara.ir/ai-chat-completions/models/list-available-models) آن (با احراز هویت) قابل بررسی‌اند؛ [کاتالوگ عمومی مدل‌ها](https://developers.liara.ir/ai-models/model-catalog-v2/list-models-with-filters) متادیتای گسترده‌تری می‌دهد. نقطهٔ پایانی BoxAPI و قالب درخواست سازگار با OpenAI آن [اینجا](https://boxapi.ir/docs/ai/#sdk) مستند شده است. این ارائه‌دهندگان آداپتور سازگار با OpenAI در AI SDK را به اشتراک دارند؛ مدل‌هایی را انتخاب کنید که از فراخوانی ابزار و خروجی ساخت‌یافتهٔ مورد استفادهٔ این موتور پشتیبانی کنند، چون پشتیبانی بسته به مدل و طرح حساب متفاوت است.

آداپتور BoxAPI در درخواست‌های BoxAPI مقدار `reasoning_effort: "none"` را از طریق گزینه‌های ارائه‌دهنده در AI SDK می‌فرستد. این با الزام فراخوانی ابزار در `/v1/chat/completions` که در خطای دروازه برای `gpt-6-luna` گزارش شده هم‌خوانی دارد؛ یافته‌های نقش‌ها و کنترل‌های ریسک قطعی فعال می‌مانند و مصرف توکن استدلال مدل برای این درخواست‌ها عموماً صفر خواهد بود.

برای آزمایش گردش کار با BoxAPI، با `gpt-5.6-luna` شروع کنید؛ کاتالوگ فعلی مدل‌ها آن را سریع و اقتصادی توصیف می‌کند. `gpt-5.6-terra` را به‌عنوان گزینهٔ متعادل مقایسه کنید و سپس برای کیفیت تصمیم `gpt-5.6-sol` یا نام مستعار `gpt-6.1-sol` موجود در فهرست مدل‌های هکاتون خود را آزمایش کنید. همهٔ نقش‌ها را با `gpt-6-astra` شروع نکنید: کاتالوگ فعلی مدل‌های متنی BoxAPI آن را ۱۰ دلار به‌ازای هر میلیون توکن ورودی و ۵۰ دلار به‌ازای هر میلیون توکن خروجی فهرست کرده و هر تصمیم موتور نقش‌های زیادی را فراخوانی می‌کند. اگر با Astra آزمایش می‌کنید، ابتدا آن را با `AI_ROLE_MODELS_JSON` به یک نقش اختصاص دهید و مصرف واقعی BoxAPI را اندازه بگیرید. این‌ها نامزدهای آزمایش‌اند، نه ادعایی دربارهٔ سودآوری معاملات؛ قیمت‌ها/دسترس‌پذیری مدل‌های BoxAPI می‌تواند تغییر کند. مدل‌های `text-embedding-3-small` و `text-embedding-3-large` مدل‌های embedding هستند نه چت؛ بنابراین نمی‌توان آن‌ها را برای `AI_MODEL` به کار برد؛ این موتور فعلاً بازیابی حافظهٔ مبتنی بر embedding ندارد. پیش از اجرای سایه، مدل انتخاب‌شده را با موتور به‌صورت آزمایشی اجرا کنید چون حلقه‌های ابزار AI SDK نیاز دارند مدل/حساب انتخاب‌شده از فراخوانی ابزار پشتیبانی کند و پیشنهاد نهایی باید اعتبارسنجی خروجی ساخت‌یافته را بگذراند.

`AI_REQUEST_TIMEOUT_SECONDS` را با `trex config set AI_REQUEST_TIMEOUT_SECONDS <seconds>` در پروفایل فعال تنظیم کنید تا یک عملیات کامل مدل محدود شود. `AI_TOOL_TIMEOUT_SECONDS` هر فراخوانی ابزار، از جمله خواندن‌های اختیاری بازار والکس، را محدود می‌کند. `AI_TIMEOUT_RETRIES` تلاش‌های دوبارهٔ محدود پس از پایان مهلت یک عملیات کامل مدل را کنترل می‌کند (۰ تا ۲؛ پیش‌فرض ۱). هر تلاش دوباره در تشخیص‌های اجرا ثبت می‌شود. خواندن‌های بازار لغو را تا درخواست HTTP منتقل می‌کنند و فقط تا زمانی که عملیات فعال است دوباره تلاش می‌کنند؛ نوشتن سفارش هرگز خودکار تکرار نمی‌شود. فیدهای زمینه‌ای اختیاری را از تنظیمات منابع دادهٔ داشبورد یا راز رمزگذاری‌شدهٔ `RESEARCH_ENDPOINTS_JSON` در پروفایل پیکربندی کنید. هر نقطهٔ پایانی با پارامترهای `symbol`، `categories` جداشده با ویرگول و `asOf` نقطهٔ زمانی پرس‌وجو می‌شود و `{ "items": [ResearchItem] }` برمی‌گرداند؛ `maxAgeSeconds` اختیاری تعیین می‌کند هر فید تا چه مدت تازه محسوب شود. اقلام کهنه و با تاریخ آینده حذف می‌شوند، اندازهٔ پاسخ محدود است و خطاهای ارائه‌دهنده به‌عنوان هشدار ثبت می‌شوند بی‌آنکه شواهد ارائه‌دهندگان دیگر پاک شود. نشانی ارائه‌دهندگان باید HTTPS باشد؛ HTTP فقط برای توسعهٔ localhost مجاز است.

اجراهای واقعی و سایه از CoinPaprika برای کاتالوگ دارایی با نماد دقیق، فیلدهای عرضه و معیارهای تجمیعی بازار به دلار و از فید RSS سایت CoinDesk برای تیترهای فعلی پرس‌وجو می‌کنند. Reddit و StockTwits همچنان با پروفایل فعال کنترل می‌شوند. وقتی پروفایل فعال کلید API ترون‌اسکن دارد، اجراهای TRX همچنین از ایندکسر شبکهٔ اصلی TRON در TronScan برای عرضهٔ در گردش، پاداش‌های تجمعی بلوک/رأی و سوزاندن کارمزد/منابع، پارامترهای فعلی زنجیره برای پاداش/کارمزد/منابع همراه با تاریخچهٔ پیشنهادهای مرتبط، تاریخچهٔ نرخ سهام‌گذاری شبکه، پیشنهادهای حاکمیتی، درآمد سوزاندن/سهام‌گذاری گزارش‌شدهٔ پروتکل و فعالیت روزانهٔ اخیر کل شبکه پرس‌وجو می‌کنند. کلید را در تنظیمات پروفایل اضافه کنید؛ TronScan برای دسترسی عادی به شبکهٔ اصلی به کلید API نیاز دارد ([ساخت کلید و احراز هویت](https://docs.tronscan.org/en/api/api-keys)، [الزامات API](https://docs.tronscan.org/en/api/common-network-auth)). تحلیل‌گران می‌توانند در صورت نیاز از DexPaprika برای نامزدهای با تیکر دقیق در بازارهای صرافی غیرمتمرکز ایندکس‌شده پرس‌وجو کنند؛ نتایج شامل شبکه و نشانی/شناسهٔ توکن هستند چون تیکرها می‌توانند تداخل داشته باشند. ممیزی اجراها وضعیت هر منبع، تعداد اقلام برگشتی/پذیرفته/واردشده و حذف‌های کهنه/آینده را ثبت می‌کند. no_matches، failed، filtered و skipped نتایج پوشش‌اند، نه اثبات اینکه رویداد یا فعالیتی رخ نداده است. ارقام CoinPaprika تجمیع‌های شخص ثالث‌اند و ممکن است تخمینی باشند؛ طرح رایگان API آن به استفادهٔ شخصی محدود است و نیازمند ذکر منبع است، پس استفادهٔ تجاری به مجوز مناسب نیاز دارد ([شرایط API](https://coinpaprika.com/api/pricing/)، [دادهٔ تیکر](https://docs.coinpaprika.com/api-reference/tickers/get-ticker-for-a-specific-coin)). اقلام CoinDesk تیتر/گزیده‌اند ([اطلاعات فید RSS](https://www.coindesk.com/coindesk-news/2021/09/17/coindesk-rss)). TronScan تجمیع‌های ایندکس‌شدهٔ پروتکل/شبکه را ارائه می‌دهد، نه بازده مخصوص یک دارنده یا تأیید کامل محلی ([عرضه و سوزاندن](https://docs.tronscan.org/en/api/statistics/funds)، [سهام‌گذاری](https://docs.tronscan.org/en/api/statistics/freezeresource)، [پارامترهای زنجیره](https://docs.tronscan.org/en/api/witness/chainparameters)، [درآمد پروتکل](https://docs.tronscan.org/en/api/protocol-revenue-service-api/turnover-new)، [حاکمیت](https://docs.tronscan.org/en/api/witness/proposal)، [فعالیت شبکه](https://docs.tronscan.org/en/api/statistics/stats-overview)). DexPaprika فقط استخرهای ایندکس‌شده را پوشش می‌دهد ([معرفی API](https://docs.dexpaprika.com/introduction)). این منابع تقویم تأییدشدهٔ آزادسازی آینده را فراهم نمی‌کنند و جذب ارزش در سطح دارندگان را ثابت نمی‌کنند؛ تحلیل‌گر توکنومیکس باید ابعاد ناموجود را «غیرقابل ارزیابی» علامت بزند. قیمت، کندل و حجم معاملات شواهد توکنومیکس نیستند.

`MARKET_QUOTE_FALLBACKS_JSON` یک مقدار رمزگذاری‌شدهٔ پروفایل است که آرایه‌ای مرتب از نقاط پایانی `{ "id", "url", "timeoutMs?", "headers?" }` را نگه می‌دارد. هر نقطهٔ پایانی `?symbol=...` را دریافت می‌کند و باید `{ "symbol", "price", "observedAt?" }` برگرداند؛ زمان‌ها برحسب میلی‌ثانیهٔ یونیکس‌اند. آن را در تنظیمات منابع دادهٔ داشبورد یا با پرسش پنهان `trex config set MARKET_QUOTE_FALLBACKS_JSON` پیکربندی کنید. والکس همچنان انتخاب اول است و برای مجوز واقعی لازم است. قیمت‌های جایگزین به‌طور مشهود با شناسهٔ ارائه‌دهنده‌شان علامت می‌خورند و نمی‌توانند از دروازهٔ ریسک واقعی عبور کنند. نشانی ارائه‌دهندگان باید HTTPS باشد؛ HTTP فقط برای توسعهٔ localhost مجاز است.

`doctor` پیکربندی، الزامات ایمنی حالت، باز شدن پایگاه داده و مهاجرت‌ها را بررسی می‌کند. با `--check-wallex` یک درخواست عمومی فقط‌خواندنی برای متادیتای بازار ارسال می‌شود تا فعال بودن جفت‌های پیکربندی‌شده بررسی شود. این دستور ارائه‌دهندهٔ AI یا هیچ نقطهٔ پایانی نوشتن صرافی را فراخوانی نمی‌کند. موفقیت آن سیم‌کشی محلی و در صورت درخواست، اتصال عمومی بازار را تأیید می‌کند؛ اطلاعات دسترسی خصوصی یا سازگاری ارائه‌دهندهٔ مدل را اعتبارسنجی نمی‌کند.

دستورهای پیش‌فرض سایه و واقعی یک چرخهٔ تصمیم انجام می‌دهند. یک چرخهٔ **واقعی** همچنان می‌تواند وقتی پیشنهاد و همهٔ بررسی‌های ریسک تأیید شوند، سفارش واقعی ارسال کند. حالت سایه جفت‌ها و پروفایل‌های استراتژی جداشده با ویرگول را می‌پذیرد؛ هر ترکیب جفت/استراتژی از یک سبد مجازی مجزا استفاده می‌کند. `--watch` ماتریس سایه را تکرار می‌کند و در کانال‌های عمومی قیمت و دفتر سفارش Centrifugo v2 والکس مشترک می‌شود. در اتصال اولیه یا اتصال مجدد، عمق بازار از REST دریافت می‌شود چون این کانال‌های عمومی دفتر اولیهٔ کامل را نمی‌دهند و بازهٔ ازدست‌رفته را بازپخش نمی‌کنند. چرخه‌های سایه هرگز `OrderExecutionPort` نمی‌سازند؛ تنها نویسندهٔ سفارش با دستور صریح `live` ساخته می‌شود.

برای یک داشبورد معاملهٔ کاغذی با به‌روزرسانی زنده، `bun run trex shadow --symbol BTCTMN --strategy agentic-balanced --watch --interval-seconds 60 --html reports/shadow-live.html` را اجرا کنید. CLI یک نشانی داشبورد محلی چاپ می‌کند (پورت پیش‌فرض 4173)؛ تا زمانی که فرایند در حال اجراست آن نشانی را باز کنید. اگر آن پورت مشغول است، `--dashboard-port 0` را بدهید تا یک پورت آزاد انتخاب شود. داشبورد فقط به `127.0.0.1` متصل می‌شود، فقط‌خواندنی است و وضعیت موتور و دادهٔ گزارش تازه‌شده را از طریق Server-Sent Events پخش می‌کند. نوار کناری آن که با صفحه‌کلید قابل دسترسی است به بخش‌های گزارش پیوند دارد؛ به‌روزرسانی‌های زنده بخش انتخاب‌شده، جزئیات باز ممیزی و فوکوس را حفظ می‌کنند. یک اسنپ‌شات HTML مستقل متناظر در هر چرخه در مسیر `--html` نوشته می‌شود و پس از توقف ناظر هم قابل استفاده می‌ماند. داشبورد عملکرد تجمعی ماندگار سبد مجازی را برای هر جفت و استراتژی، حتی پس از راه‌اندازی مجدد فرایند، نشان می‌دهد. هر چرخه همچنین به‌عنوان اجرای جداگانه در `status` و `report` در دسترس است. حالت سایه از موجودی معاملاتی صرافی استفاده نمی‌کند و نمی‌تواند سفارش ارسال کند. پرشدن‌های کاغذی آن اجرا را از یک اسنپ‌شات تازهٔ عمق قابل مشاهده به‌علاوهٔ کارمزد و لغزش پیکربندی‌شده تخمین می‌زنند؛ اولویت صف، تأخیر صرافی، نقدینگی پنهان، پذیرش سفارش یا اثر بازار فراتر از لغزش پیکربندی‌شده را مدل نمی‌کنند. نتایج سایه چرخهٔ عمر دستیار و سبد را به کار می‌اندازند اما نمی‌توانند پرشدن یا بازده واقعی را تضمین کنند. فراخوانی API مدل همچنان می‌تواند هزینه داشته باشد؛ برای پرهیز از هزینهٔ استنتاج خارجی، `AI_PROVIDER=compatible` و `AI_BASE_URL` را در یک پروفایل پایگاه داده پیکربندی کنید و آن‌ها را به یک سرور مدل محلی سازگار با OpenAI که از فراخوانی ابزار و خروجی JSON ساخت‌یافته پشتیبانی می‌کند اشاره دهید.

گزارش HTML مستقل شامل نمودارهای نرمال‌شدهٔ ارزش دارایی و افت سرمایه؛ عملکرد جفت/استراتژی؛ پیکربندی و فرض‌های اجراهای اخیر؛ هر تصمیم، قیمت، پیشنهاد، استدلال، شواهد و یافتهٔ دستیار ذخیره‌شده؛ بررسی‌های ریسک قطعی؛ قصدهای سفارش و پرشدن‌ها؛ اسنپ‌شات‌های سبد؛ اسنپ‌شات‌های منابع؛ و نتایج/بازتاب‌های حافظه است. جزئیات سبد شامل وجه نقد، ارزش روز موقعیت‌ها، سود/زیان تحقق‌نیافته، سود/زیان تحقق‌یافتهٔ امروز، کارمزدها و سود/زیان کل ارزش دارایی است. قابلیت اطمینان اجرا فقط وقتی نشان داده می‌شود که یک پیشنهاد سفارش مسیر اجرا را به کار گرفته باشد؛ اجرایی که فقط HOLD داشته «Not exercised» علامت می‌خورد، نه ۱۰۰٪ قابل اطمینان. شکست‌های اجرای تازه‌ثبت‌شده نام و پیام خطای پاک‌سازی‌شده دارند؛ علت شکست‌های قدیمی‌تر که در همان زمان ثبت نشده‌اند قابل بازیابی نیست. فعالیت AI بر اساس نقش دستیار، ارائه‌دهنده/مدل پیکربندی‌شده، وضعیت مرحله، مدت، دلیل پایان، نام ابزارها، توکن‌های ورودی/خروجی/استدلال/کل گزارش‌شدهٔ ارائه‌دهنده، هشدارها و جزئیات فراخوانی‌های ناموفق ممیزی می‌شود. این گزارش عمداً پرامپت کامل یا آرگومان ابزارها را ذخیره نمی‌کند. هزینهٔ ارائه‌دهنده تخمین زده نمی‌شود چون قیمت مدل‌ها و تخفیف‌ها بسته به حساب متفاوت‌اند و می‌توانند تغییر کنند؛ برای هزینهٔ صورتحساب‌شده از صفحهٔ مصرف ارائه‌دهنده استفاده کنید. `shadow --audit-limit 100` تعیین می‌کند چند ممیزی اجرای اخیر در گزارشی که پیوسته تازه می‌شود جاسازی شود؛ تجمیع عملکرد همچنان همهٔ اجراهای کامل‌شده را پوشش می‌دهد. `report --audit-limit 50 --html reports/recent.html` پنجرهٔ داشبورد اجراهای اخیر را کنترل می‌کند، در حالی که `report <run-id> --html reports/run.html` ممیزی کامل ماندگار همان اجرا را شامل می‌شود. اجراهای قدیمی‌تر در SQLite می‌مانند و جداگانه قابل باز شدن‌اند.

**معاملهٔ واقعی** یعنی دستور انتخاب‌شده اجازه دارد سفارش واقعی به حساب اعتباری والکس پیکربندی‌شده بفرستد؛ `live` ساده یک چرخه اجرا می‌کند و ممکن است سفارش واقعی ارسال کند. **معاملهٔ خودکار** نسخهٔ تکرارشونده و بدون نظارت معاملهٔ واقعی است: پیوسته در فاصلهٔ تعیین‌شده چرخه اجرا می‌کند و هر بار ممکن است سفارش واقعی ارسال کند. این حالت علاوه بر `WALLEX_ENABLE_LIVE_TRADING=true`، مقدار مثبت `LIVE_MAX_GROSS_EXPOSURE` و همهٔ بررسی‌های دیگر حالت واقعی، به پرچم صریح `live --auto-trade` و ذخیرهٔ `WALLEX_ENABLE_AUTOTRADING=true` در پروفایل فعال پایگاه داده نیاز دارد. دستور خودمختار به یک جفت و یک استراتژی در هر فرایند محدود است و با خطای اجرا یا بازیابی متوقف می‌شود. یک پرچم پیکربندی به‌تنهایی معامله را آغاز نمی‌کند؛ دستور صریح هم لازم است.

استراتژی‌های داخلی عبارت‌اند از `agentic-balanced`، `momentum`، `mean-reversion` و `capital-preservation`. تنظیم `ENGINE_STRATEGIES_JSON` در پروفایل پایگاه داده می‌تواند پروفایل اضافه کند یا یک استراتژی داخلی را با شناسهٔ آن جایگزین کند؛ داشبورد ویرایشگر راهنمای استراتژی دارد. هر پروفایل مأموریت، حداقل اطمینان و انواع سفارش مجاز خود را می‌دهد؛ سقف‌های اختیاری `maxOrderNotional`، `maxPositionNotional` و `maxGrossExposure` به پروفایل‌ها اجازه می‌دهند بودجهٔ ریسک متفاوتی داشته باشند. اطمینان، قواعد نوع سفارش و سقف‌های ریسک پس از خروجی مدل به‌صورت قطعی اعمال می‌شوند. نقش‌ها و استراتژی‌ها را جداگانه پیکربندی کنید تا انتخاب مدل و مأموریت معاملاتی به‌عنوان متغیرهای جداگانه قابل سنجش باشند.

برای مثال، `ENGINE_STRATEGIES_JSON=[{"id":"breakout","name":"Volume confirmed breakout","mandate":"Trade only a close above the recent completed range with confirming volume; otherwise HOLD.","minConfidence":0.75,"allowedOrderTypes":["LIMIT"]}]` یک پروفایل اضافه می‌کند. مأموریت به زبان طبیعی دستیارها را هدایت می‌کند؛ حداقل اطمینان و انواع سفارش مجاز دروازه‌های سخت قطعی‌اند.

دستورهای آزمایش تاریخی و سایه مقایسه‌های عملکرد JSON مورد به مورد تولید می‌کنند. گزارش HTML سایه همهٔ چرخه‌های کامل‌شدهٔ هر سبد مجازی مجزا را تجمیع می‌کند. `--html` یک داشبورد خودکفا با نمودارهای نرمال‌شدهٔ ارزش دارایی و افت سرمایه، کارت‌های امتیاز عملکرد و جدول‌های مقایسه، پیکربندی و فرض‌های اجرا، جزئیات تصمیم/شواهد/مناظره، نتایج ریسک، ممیزی سفارش/پرشدن، اسنپ‌شات منابع، ارزیابی‌های حافظه و تله‌متری مصرف AI به تفکیک مرحله می‌نویسد. `--audit-limit` جزئیات اجراهای اخیر جاسازی‌شده در داشبوردهای سایه/اجراهای اخیر را محدود می‌کند؛ معیارهای عملکرد تجمعی همچنان از تاریخچهٔ کامل ذخیره‌شده استفاده می‌کنند. مبنای خرید و نگهداری در اولین باز شدن قابل اجرای بازهٔ بعدی وارد می‌شود و فرض‌های کارمزد و لغزش پیکربندی‌شده را در ورود و خروج اعمال می‌کند؛ این یک مرجع شفاف فقط‌خرید است، نه یک شاخص قابل سرمایه‌گذاری.

عملکرد به کل گردش کار دستیارها برای هر پروفایل جفت/استراتژی نسبت داده می‌شود. نقش‌های تحلیل‌گر و بازبین ریسک شواهد فراهم می‌کنند و پیشنهادها را بررسی می‌کنند؛ آن‌ها سبد مستقلی اجرا نمی‌کنند، بنابراین سود/زیان مجزای آن‌ها گزارش نمی‌شود.

### مناظره و حافظهٔ نتیجه

گردش کار از ترتیب گراف پروژهٔ پایتون پیروی می‌کند: چهار تحلیل‌گر هم‌زمان اجرا می‌شوند؛ پژوهشگران صعودی و سپس نزولی برای هر دور مناظرهٔ پیکربندی‌شده نوبت می‌گیرند؛ مدیر پژوهش یافته‌هایشان را ترکیب می‌کند؛ معامله‌گر یک نامزد می‌سازد؛ تحلیل‌گران ریسک تهاجمی، محافظه‌کار و بی‌طرف برای هر دور ریسک پیکربندی‌شده به ترتیب بررسی می‌کنند؛ و مدیر سبد پیشنهاد نهایی را می‌دهد. پیش‌فرض‌ها با یک دور کامل صعودی/نزولی و یک دور کامل ریسک با سه بازبین در پروژهٔ پایتون مطابقت دارند. محدودهٔ دورها ۱ تا ۱۰ است و هر یافتهٔ تکراری با شمارهٔ نوبت و یافته‌های پیشین در ممیزی تصمیم نگه داشته می‌شود.

هر تصمیم نهایی BUY، SELL یا HOLD یک ورودی حافظهٔ در انتظار می‌سازد. این ورودی فقط پس از سپری شدن کامل پنجرهٔ نگهداری پیکربندی‌شده امتیازدهی می‌شود: ورود با اولین بسته شدن کامل پس از تصمیم انجام می‌شود و سپس تعداد پیکربندی‌شدهٔ بازه‌های یک‌دقیقه‌ای نگه داشته می‌شود. حافظه بازده دارایی، بازده معیار، آلفا، قیمت‌ها، زمان‌ها، تز تصمیم و یک بازتاب کوتاه تولیدشده با AI را ذخیره می‌کند. به‌طور پیش‌فرض معیار، BTC جفت‌شده با ارز بازار پایهٔ آن بازار است؛ `MEMORY_BENCHMARK_SYMBOL` می‌تواند آن را تغییر دهد. اگر تاریخچهٔ قیمت یا تولید بازتاب در دسترس نباشد، رکورد در انتظار می‌ماند و می‌تواند در چرخهٔ بعدی دوباره تلاش شود. یک درس تسویه‌شده فقط در زمان حل‌وفصل یا پس از آن برای زمینهٔ دستیارها واجد شرایط می‌شود؛ آزمایش‌های تاریخی همان حد را اعمال می‌کنند تا نشت نتیجهٔ آینده رخ ندهد. در صورت وجود، پنج درس اخیر همان جفت و سه درس از جفت‌های دیگر برای همان حالت و استراتژی ارائه می‌شوند.

افق پیش‌فرض حافظه `MEMORY_HOLDING_PERIOD_BARS=7200` است (پنج روز در بازارهای ۲۴/۷ رمزارز)، معادل رمزارزی پیش‌فرض پنج روز معاملاتی در موتور پایتون. `report <run-id>` رکوردهای حافظهٔ در انتظار و تسویه‌شده را برای ممیزی شامل می‌شود. این بازده‌های حافظه پیش‌بینی بازار در تصمیم را نسبت به BTC ارزیابی می‌کنند؛ سود/زیان حساب نیستند. برای ارزیابی عملکرد واقعی استراتژی از ارزش دارایی سبد، کارمزدها و پرشدن‌ها در گزارش‌های آزمایش تاریخی/سایه استفاده کنید.

## حالت‌ها و ایمنی

- **آزمایش تاریخی** تاریخچهٔ OHLCV یک‌دقیقه‌ای والکس را می‌خواند و فقط کندل‌های کامل‌شده را در نظر می‌گیرد. سیگنال یک بازهٔ بسته‌شده زودتر از باز شدن بازهٔ بعدی پر نمی‌شود. فیدهای فعلی اخبار، احساسات، توکنومیکس و آن‌چین حذف می‌شوند چون دادهٔ تاریخی نقطه‌زمانی نیستند. فرض‌های کارمزد و لغزش در گزارش اجرا ذخیره می‌شوند. این حالت ادعای دقت دفتر سفارش تاریخی، جایگاه در صف یا اجرای درون‌بازه را ندارد؛ مدل زبانی انتخاب‌شده هم ممکن است دانشی داشته باشد که در زمان تصمیم تاریخی در دسترس نبوده است.
- **سایه** از دادهٔ زندهٔ بازار والکس، ارائه‌دهندگان زمینه‌ای، عمق قابل مشاهدهٔ فعلی دفتر و یک سبد مجازی مجزا برای هر جفت/استراتژی استفاده می‌کند. هیچ مسیر API برای ایجاد/لغو سفارش ندارد.
- **واقعی** به زیردستور صریح `live`، فعال‌سازی معاملهٔ واقعی، کلید API و شناسهٔ مشتری اختصاصی حساب اعتباری، یک بازار اسپات فعال در فهرست مجاز، بررسی محدودیت بسته، قیمت تازهٔ والکس و عبور از بررسی ریسک قطعی نیاز دارد. بلافاصله پیش از ارسال، یک بررسی ریسک تازه دوباره انجام می‌شود.

ارسال سفارش واقعی پیش از POST، یک قصد (intent) و `client_id` یکتای والکس را ذخیره می‌کند. یک اجارهٔ (lease) SQLite از هم‌پوشانی اجراکننده‌های واقعی یا سایه جلوگیری می‌کند؛ اجاره‌های رهاشده پس از کرش منقضی می‌شوند. در صورت پایان مهلت یا خطای اتصال، موتور جزئیات سفارش و سفارش‌های باز را برای همان شناسهٔ مشتری بررسی می‌کند و هرگز درخواست ایجاد را خودکار تکرار نمی‌کند. قصدهای نامشخص یا هنوز باز، معاملهٔ جدید را تا تطبیق وضعیت متوقف می‌کنند. پرشدن‌ها و جزئیات سفارش از پاسخ‌های REST والکس ثبت می‌شوند. کلیدهای API در پیکربندی اجراها یا گزارش‌ها گنجانده نمی‌شوند.

`cancel-order` فقط شناسهٔ مشتری مرتبط با یک قصد ماندگار حالت واقعی را می‌پذیرد. از همان اجارهٔ اجراکنندهٔ واقعی استفاده می‌کند، سفارش متناظر والکس را لغو می‌کند و هر پرشدنی را که صرافی گزارش دهد ثبت می‌کند. این دستور وقتی فعال‌سازی معاملهٔ واقعی یا کلید توقف اضطراری ریسک ارسال جدید را مسدود کرده نیز در دسترس می‌ماند.

سقف‌ها و کلیدها را با `LIVE_MAX_GROSS_EXPOSURE`، `RISK_MAX_ORDER_NOTIONAL`، `RISK_MAX_POSITION_NOTIONAL`، `RISK_MAX_GROSS_EXPOSURE`، `RISK_MAX_DRAWDOWN_PCT`، `RISK_MAX_DAILY_LOSS`، `RISK_MAX_DATA_AGE_SECONDS`، `RISK_FEE_BUFFER_BPS`، `RISK_MAX_MARKET_SLIPPAGE_BPS` و `RISK_KILL_SWITCH` پیکربندی کنید. `LIVE_MAX_GROSS_EXPOSURE` یک سقف سخت اضافی فقط برای حالت واقعی روی همهٔ موقعیت‌های ارزش‌گذاری‌شده برحسب ارز بازار پایه است، شامل موقعیت‌هایی که از قبل در زیرحساب هستند به‌علاوهٔ سفارش پیشنهادی؛ سقف مؤثر کمترینِ آن، سقف کلی درگیری سرمایه و سقف استراتژی است. این سقف درگیری سرمایهٔ ایجادشده توسط این موتور را محدود می‌کند، نه زیان در جاهای دیگر یا رفتار جداگانهٔ اعتبار/لیکوئید والکس را. دروازه‌های افت سرمایه و زیان روزانه سفارش‌های جدید را متوقف می‌کنند؛ آن‌ها موقعیتی را خودکار نمی‌بندند و قیمت توقف را تضمین نمی‌کنند. یک جهش سریع قیمت می‌تواند پیش از آنکه چرخهٔ بعدی ریسک را بررسی کند زیان بزرگ‌تری ایجاد کند. تا زمانی که موتور اجرا می‌شود از زیرحساب اعتباری فقط برای این موتور استفاده کنید تا یک سفارش دستی هم‌زمان نتواند با اسنپ‌شات موجودی آن رقابت کند. دقت مقدار و قیمت بازار با متادیتای والکس بررسی می‌شود؛ فروش اسپات نمی‌تواند از مقدار دارایی پایهٔ در دسترسِ ثبت‌شده بیشتر باشد. سفارش‌های بازار واقعی به عمق قابل مشاهدهٔ تازه و کافی برای کل سفارش نیاز دارند و وقتی لغزش تخمینی از حد پیکربندی‌شده بیشتر شود رد می‌شوند. موجودی حساب از [نقطهٔ پایانی جزئیات موجودی زیرحساب اعتباری](https://developers.wallex.ir/docs/generated/sub-account-balances-details) والکس خوانده می‌شود و دارایی‌هایی که نتوان آن‌ها را نسبت به `WALLEX_QUOTE_CURRENCY` ارزش‌گذاری کرد، عملیات واقعی را متوقف می‌کنند.

## ردّ ماندگار بازبینی

مهاجرت‌های SQLite جدول‌هایی برای اجراها، اسنپ‌شات منابع، تصمیم‌ها و استدلال‌ها، نتایج ریسک، قصدهای سفارش، پرشدن‌ها، اسنپ‌شات سبد، اجاره‌های اجرا، نقاط بازیابی، حافظه‌های تصمیم در انتظار/تسویه‌شده، بازتاب‌ها و تله‌متری فراخوانی مدل AI می‌سازند. هر تصمیم قیمت، شواهد پژوهشی با منبع/زمان/اطمینان، یافته‌های دستیارها، استراتژی انتخاب‌شده، پیشنهاد نهایی، نتیجهٔ ریسک قطعی و چرخهٔ عمر حافظه را ذخیره می‌کند. `report <run-id>` شواهد تصمیم، نتایج ریسک، سفارش‌ها/پرشدن‌های مرتبط، امتیازها و بازتاب‌های حافظهٔ تصمیم، وضعیت ارائه‌دهنده/مدل/توکن/زمان‌بندی هر مرحله و تاریخچهٔ کامل سبد را شامل می‌شود؛ با `--include-backtest-data` کندل‌های تاریخی استفاده‌شده برای اجرا و معیار آن هم اضافه می‌شوند. آزمایش‌های تاریخی پس از راه‌اندازی مجدد، تصمیم‌ها و نقاط بازیابی ماندگار هر بازه را دوباره استفاده می‌کنند تا فراخوانی تکراری مدل یا پرشدن شبیه‌سازی‌شدهٔ تکراری رخ ندهد. برای بازتولید یک اجرا، نسخه‌های پشتیبان SQLite را همراه با پیکربندی مربوط و فایل قفل وابستگی‌ها نگه دارید.

ارائه‌دهندگان AI پیکربندی‌شده زمینهٔ تصمیم، از جمله موجودی‌ها و موقعیت‌های سبد، را دریافت می‌کنند. رکوردهای اجرا انتخاب مدل‌ها و شناسهٔ ارائه‌دهندگان را نگه می‌دارند اما کلیدهای API، نشانی نقاط پایانی و هدرهای سفارشی را حذف می‌کنند.

خروجی اجراها شامل بازده خالص، بیشترین افت سرمایه، تعداد معاملات (پرشدن‌ها)، حجم، میانگین اندازهٔ پرشدن، قابلیت اطمینان اجرا، کارمزدها به تفکیک دارایی کارمزد، اثر لغزش برحسب ارز بازار پایه و فرض‌های اعلام‌شده است.
